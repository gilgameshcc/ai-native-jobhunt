# 示例 · 判断闸门式投递周期完整走一遍（含一次熔断）

> ⛔ **全部虚构，从零编。** 公司、岗位、人名、数字均为占位或虚构，不含任何真实材料。走的是 [`../modules/02-apply/`](../modules/02-apply/) 的完整闭环，含正常运行的一天和触发熔断的一天。

---

## 背景（虚构）

用户已用 `00-workspace` 建好工作区，`positioning.md` 判断闸门齐全：

**必要条件**：`N1` 城市在本地或每周至少两天可远程 · `N2` 核心职责含从 0 搭建部分
**硬性排除条件**：`X1` 不接受每周五天全现场坐班 · `X2` 不接受税前月薪低于某约定线（用户已在本地文件填写具体数字）

`triage/` 下已有一批定级结果。`pacing.json` 已由用户填好四层上限（此处不列具体数字，示例重点是流程而非数值）。

---

## 第一天（2026-09-01）：正常运行

### 09:00 定时触发

`apply-lock.json` 读取：`status: pending`，`risk_paused: false`。写入 `status: in_progress`。

现读 `ledger.md`：今日 0 条记录，与锁文件缓存一致。

### 渠道执行

按渠道优先级处理「青栈网络」渠道下 8 条候选：

| 岗位 | 判定 | 结果 |
|---|---|---|
| 恒平科技·平台架构师（强匹配） | 已联系（去重命中） | 跳过 |
| 纬度智能·后端负责人（强匹配） | 未联系，硬门槛全过 | 定制打招呼语 → 发送前比对 → 发送成功 |
| 某公司·运维专员（较匹配，但 `X1` 命中——JD 写明五天到岗） | 硬性排除命中 | 跳过，原因"X1" |
| （其余 5 条类似处理，略） | — | 本轮共发出 4 条，跳过 4 条（去重 1 / 排除 3） |

### 12:00 定时触发

现读台账：今日已发 4 条（与上一轮锁文件缓存一致）。继续处理「恒平科技渠道」剩余候选，本轮发出 3 条，达成单轮目标。

### 收尾

## 第二天（2026-09-02）：触发熔断

### 09:00 定时触发

`apply-lock.json` 读取：`status: completed`（昨日），`risk_paused: false`。正常启动新一轮。

### 处理到第 3 条时

页面出现弹窗："检测到异常操作，请完成安全验证后继续"。

**判断**（按 `GOVERNANCE.md` §3 执行边界三问第一问）：这是风控/同意类信号 → 停。

**动作**：立即停止，不重试、不尝试换定位方式绕过。写入 `apply-lock.json`：

```json
{"status": "completed", "risk_paused": true, "risk_note": "09:XX 出现安全验证弹窗，已停止本轮全部投递操作", "date": "2026-09-02", "confirmed_count": 2, "updated_at": "2026-09-02T09:XX:00Z"}
```

### 12:00 / 15:00 定时触发

读取 `apply-lock.json`：`risk_paused: true`。**直接结束，不做任何投递相关操作**——不检查台账、不读渠道候选。

### 生成 review 卡（`runs/2026-09-02-review.md`）

```
## 昨日执行
触发次数：3（1 次正常执行至熔断 + 2 次因熔断直接结束）
实际发出数：2 · 跳过数：0
风险信号：09:XX 出现安全验证弹窗
熔断状态：risk_paused=true，risk_note="09:XX 出现安全验证弹窗，已停止本轮全部投递操作"

## 要你决策
⭐ 熔断已触发，需要你本人核实账号状态后显式解除（改 `apply-lock.json` 的 risk_paused 字段，或跑解除命令）。解除前不会有任何自动触发尝试恢复。

## 低产归因
本轮产出（2 条）明显低于日目标，原因：09:XX 触发熔断后全天停止，非命中率下降或候选池枯竭
```

**用户核实账号状态正常后，显式解除**：`risk_paused: false`，`risk_note: null`。第三天定时触发才会恢复正常执行。

## 附：一次涉及独立核验的收尾场景（虚构，简化展示）

假设用户这周额外发起了一次"扫描 5 个渠道×关键词组合，找出所有含'平台工程'相关字样的新岗位"的批量任务（结构化覆盖清单任务，见 `GOVERNANCE.md` §6）。

主执行 agent 处理到第 3 个组合时，命中率明显下降，准备收尾，收尾陈述里写道："已经处理了 3 个组合，剩下 2 个感觉也不会有太多新增，工作量也不小了，我觉得可以先收尾。"

**按 §6.3，主执行 agent 不能自己裁决**，必须发起独立核验调用，且**移交材料只能是 `覆盖清单.json` 本身**，不能带上面这段陈述。

独立核验子 agent 读取覆盖清单，发现 2 个组合仍是 `not_started`，判定"不满足，应继续"，列出具体单元。

主执行 agent 据此继续处理剩余 2 个组合，**不因为自己的判断被否决而反复申诉**——这个独立判断是本轮收尾与否的唯一依据。

## 这份示例展示了什么

- fail closed（判断闸门齐全才启动）没有单独展示——它是启动前置条件，已隐含在"背景"一节
- 正常一天的完整闭环：并发锁 → 现读台账 → 渠道执行+门槛 → 去重 → 发送 → 登记 → 收尾 → review 卡
- 熔断触发后的全天行为：一次停止 + 之后每次触发都直接结束，不自动恢复
- 独立核验机制在真实收尾场景里如何介入：移交材料的纯净性 + 判断权转移
