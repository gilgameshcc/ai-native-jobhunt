# GOVERNANCE · 让自动化不失控的判断层

> 与 [`SKILL.md`](SKILL.md) 配套使用。工作量默认值见 [`config/pacing.json`](config/pacing.json)，本地工具用法见 §7。

---

## 1. 工作量、计数与续接

Agent 将公开预设复制到私人 `policies/pacing.json`，已有配置先保留。该文件是实际参数的唯一来源，`preferences.md` 只引用它。用户已经给目标和发送范围时，直接选用有效预设，记录采用值，不要求再次确认全部批次参数。只有参数无效、必要条件或权限确实缺失时才补真实缺口。

- `daily_target`：当天希望完成的**已核实成功的唯一申请数**。
- `daily_cap`：当天硬预算；**成功＋待核实＋发送中＋已占额未发送**共同占额。
- `round_target`：本轮成功目标；`batch_size` 与 `session_max_batches` 限制本会话发送尝试。
- 轮目标或会话上限到达后结束当前轮，未到日目标且有预算、候选和执行能力时继续下一轮；没有实际调度时不能宣称后台已经启动。

预设支持日目标100–150；数量属于 `default_advisory` 工作量配置，不是平台安全值。按页面就绪、平台明确限制和用户可用窗口执行，不要求随机停留、随机浏览或逐项人工校准。

每个岗位使用稳定 `application_key`：优先统一雇主、岗位和地点的身份，跨渠道同岗位复用同一键。仅用平台局部ID时不能声称已完成跨渠道去重，仍需Agent对照职位证据归并。正式申请回执或已核实的首次岗位接触可作为该渠道的完成证据；跟进、读取、点击按钮和收到推荐不增加新申请数。

发送前原子占额，进入可能产生申请的外部动作前记 `sending`。确认成功转 `confirmed`；结果不明转 `pending`，保留占额且不重发；有明确未发送证据才转 `not_sent` 并释放占额，重试仍按 §3 有界执行。迟到确认只改变原记录状态，不新建第二个成功事件。

按发送发生时间与配置时区归日。次日核实的旧申请修正原发送日，不挤占新日目标；全局去重、不明项和风险状态跨日保留。跨午夜尚未发送的占额先释放，再按新日配置重新占额。工具的运行状态库是发送计数事实源，台账自动区块只是投影；原始接触与回应原话继续保留，不能把台账行数或锁缓存当成功数。

## 2. 熔断

**触发源限定为强语义信号**：验证码、异地登录提醒、异常操作提示、账号异常状态页。**不是**"命中率下降""跑得有点慢"这类正常波动。

**一旦触发，持久保存风险暂停**；工具模式执行 `pause --evidence <实际信号>`。后续发送直接拒绝。普通日预算、轮目标、会话上限耗尽只结束相应轮次，不设置风险暂停。

**解除必须有明确的人工恢复指令与记录**。工具模式由本人运行 `resume-risk --evidence <处理说明>`，或在本人明确要求解除后由Agent执行并保存该授权；不能将普通“继续任务”推断为解除风险。旧 `apply-lock.json` 的风险状态会在首次迁移导入，修改其缓存字段不能清除工具中的暂停。已有Host的独立风险状态仍由其管理入口处理，不能用本地工具替代Host解除。

⛔ **不允许因为"已经过了一段时间、应该没事了"而自动恢复。** 熔断状态没有超时自愈机制，这是有意的设计——风控信号的持续时间对 agent 不可见，自动超时恢复等于在赌一个自己看不到的变量。

## 3. 执行边界三问

自动化流程里的失败分两种性质完全不同的情况，处理方式必须不同：

**遇到卡点时，按顺序自查：**

1. **这是风控、本人身份核验或超出原授权的同意请求吗？** → 是，暂停受影响的动作；风控按 §2 停止。不重试、不换方式绕过。已授权动作的普通确认提交界面，由 Agent 核对对象、材料和动作后完成，不归为新增授权。这条优先级最高
2. **这是纯技术执行问题吗？** 先区分只读操作与可能已生效的发送。只读连接失败、页面读取超时可重试一次；仍失败就记录并转 L3，不用“换方式”重置次数。发送后超时或页面状态不明，先只读核实，并记台账“结果待核实”；未取得明确未发送证据前，不重发该条，也不计入已确认成功。已经成功则登记并跳过；明确未发送才可在原授权和节奏预算内重试一次。风控信号始终按第一问停止。
3. **这是规则能裁决的业务判断吗？**（这条要不要投、要不要发这条打招呼语）→ 是，按既定规则自主判断，拿不准就按更保守的一侧判断，事后记录理由，不停下来问

**只有真正卡在"规则没覆盖、又不是技术问题、又不是风控信号"的情况，才值得打断汇报。**

## 4. 提前结束白名单

**以下情况可以结束本轮或暂停交付**，命中哪一种及实际完成范围要写进 review 卡：

1. **命中风控信号**（熔断触发）
2. **候选池确实枯竭**——所有渠道各扫过一轮，且去重命中率持续很高（意味着大部分候选都已处理过）。⚠️ **如果本轮任务定义了结构化覆盖清单（见 §6），这一条必须由独立核验确认，不能自己判断"差不多枯竭了"**
3. **达成轮目标或日目标**
4. **触及单次会话上限**
5. **当前可执行范围已被具体阻塞**——工具明确拒绝动作、仅有只读能力，或剩余条目都待本人身份核验/新增决定，且已没有不受影响的授权工作可继续。交付已完成的材料、待处理条目和继续条件，保持未完成状态；不把阻塞伪装成候选池枯竭或目标已达成。单条阻塞只暂停该条。真实风控仍按 §2 停止。
6. **当天硬预算已占满或日期已切换**——结束当前轮并保留实际成功/不明数量；普通预算结束不写风险暂停。进入下一日或下一轮时重新核对剩余额度，旧日未发占额先释放。

**反面清单——以下都不构成提前结束的理由**：

- "逐条核对文本"（这是正常步骤的成本，不是可以跳过换速度的地方）
- "工具调用次数多"
- "感觉工作量大"
- "命中率看起来在下降"（下降不等于枯竭，见白名单第 2 条的区分）
- "跑得有点久了"

⛔ **这份反面清单本身也是一份需要独立核验的清单**——见 §6：执行者如果在收尾陈述里说出反面清单上的理由，独立核验子 agent 必须直接判定"不满足停止条件"，不接受这类理由作为收尾依据。

## 5. 汇报边界

**有明确数量/进度目标的任务，在目标达成之前，不主动停下来做阶段性总结，也不用"要不要继续"这类暗示性收尾结束任务。** 过程中出现的新情况（比如收到对方回复）记入台账备注即可，不需要单独打断任务去汇报。真正要收尾时，一次性给完整汇报（即每日 review 卡）。

这条和 §3 执行边界三问是两回事：一个管"要不要打断任务问问题"，一个管"要不要打断任务汇报进度"，默认答案都是不要，除非明确命中风控信号这类必须停的情况。

## 6. 长周期批量任务的收尾：结构化覆盖清单 + 独立核验

**这一节解决的是一个具体的、真实反复发生的失效模式**：即使把停止条件写得足够具体，执行 agent 仍然会在长会话里因为工作量大、命中率下降、会话变长这类疲劳类模式，自行判断"可以收尾了"——哪怕它自己刚刚在收尾陈述里承认"还有几个组合没扫完"，结论仍然是"可以停"。

**根因不是规则不够细。** 停止判断依赖执行者对自身进度的**叙述性自评**，而不是对**结构化状态的机械核对**。自然语言总结天然允许"基本""大部分""差不多"这类模糊量词，判断"是否该停"和"执行任务本身"由同一个身份、在同一次输出里完成，缺乏独立视角校验——这是一种结构性的利益冲突，靠给这个身份加更多文字规则解决不了，因为规则也是由同一个可能存在乐观偏差的判断过程去执行的。

**同一类问题补丁式修订三次以上仍复发，应该怀疑机制本身，不是继续加细则。**

### 6.1 什么任务需要这套机制

任何"有明确数量/覆盖目标、多轮次执行、执行者可能因为工作量大或战果变少而提前收尾"的自动化任务，**不限于本模块**。典型场景：扫描多个渠道 × 多个关键词组合、批量核实一份候选清单、任何"要枚举完一个有限但较大的集合"的批处理。

**不需要这套机制的场景**：单次触发只处理台账里已经确定的一批 JD（数量有限、范围本身就是台账内容，不存在"扫描空间还有多少没覆盖"这个问题）。是否需要，看任务本身是否存在一个"结构上可枚举、但执行者容易低估剩余规模"的搜索/扫描空间。

### 6.2 第一步：把任务范围拆解成结构化、可枚举的覆盖单元清单

**落地成独立文件，不是写在执行者的自然语言汇报里。** 覆盖单元要足够细、足够客观，能用"未开始 / 进行中 / 已完成"这种机械状态描述，不依赖主观判断。

最小字段设计（`runs/<date>-覆盖清单.json`，运行时状态文件，不是跨模块契约）：

```json
{
  "周期标识": "本轮的唯一标记，例如日期或批次号",
  "覆盖单元": {
    "<渠道>×<关键词组合1>": {
      "status": "not_started | in_progress | done",
      "最近处理时间": "ISO 时间戳",
      "本轮新增候选数": 0,
      "去重命中数": 0
    },
    "<渠道>×<关键词组合2>": { "...": "..." }
  }
}
```

**执行过程中要实时更新这份清单**——处理完一个单元立刻写状态，不要等任务结束时凭印象回忆补一份。这一步本身是关键：如果状态只在结束时批量回填，仍然会退化成"事后叙述"，失去机械核对的意义。

### 6.3 第二步：收尾判断权从执行者转移给一次独立的 agent 调用

主执行 agent 想要结束当前轮次之前，**必须调用一个独立的子 agent（全新上下文，看不到主执行 agent 的对话历史和自我叙述）**，给它一个范围明确、输入受限的任务：

- **只依据实际结构化状态**（覆盖清单 + `ledger.md` 对应记录 + 预算工具status/运行库的独立只读查询），旧锁缓存不代替当前运行状态；**不接受主执行 agent 转述的"进度总结"作为输入**。如果子 agent 的依据混入执行者自己的叙述，独立性就被污染了
- 逐条对照 [§4 提前结束白名单](#4-提前结束白名单)，给出「满足 / 不满足」的布尔判断，**并写明依据的具体数字或状态**（不允许用"基本""大致"这类模糊措辞代替逐项核对）
- 结束/暂停条件择一命中即可；没有命中任何条件时，返回"应继续执行"，列出仍可执行的 `not_started` / `in_progress` 单元。命中具体阻塞时核实其证据，区分仍可继续的单元与受阻未完成的单元；已无可继续工作则返回"可暂停，未完成"，列出阻塞及接续条件，不判成覆盖完成
- 明确风险信号优先停止；反面措辞检查不能推翻风险暂停或要求继续发送
- ⛔ **如果主执行 agent 在准备移交给子 agent 的材料里出现 §4 反面清单上的措辞（"感觉工作量大""命中率在下降"等），子 agent 必须直接判定不满足停止条件，不需要再核对其他项**——这是反面清单的机械执行点

**独立核验的调用方式**：可以是同一 agent 产品里发起的一次独立子任务调用（多数 agent 产品都有这类子任务 / 子 agent 工具），关键约束是**这次调用不带入主任务的对话历史**，只接收上面列出的结构化文件作为输入。如果你的 agent 运行时不支持发起独立子调用，退化方式是：**开一个全新的对话会话**，只把覆盖清单文件和台账贴进去，让它独立判断，再把结论带回主任务——效果等价，只是操作上多一步。

**主执行 agent 必须把这个独立判断当成收尾与否的唯一依据**：子 agent 说"应继续"，主执行 agent 就不能因为"自己觉得已经做了很多、读了很久、命中率变低"而自行推翻；子 agent 的判断和完整依据要写回覆盖清单文件（补一个 `独立核验结论` 字段），留下"这一步确实被独立核验过"的痕迹。

### 6.4 这个机制的价值边界

它解决的是"执行者用模糊叙述给自己找收尾借口"这一种失效模式，**不能替代"停止条件本身该怎么定义"这个更上游的判断**——条件定义得不合理，独立核验只会更精确地执行一个错误标准。所以这个机制必须和 §4 明确、可枚举、无歧义的停止条件搭配使用，不能单独依赖它。

**如果发现子 agent 反复卡在某条停止条件上给不出干脆的布尔判断，说明该回头修的是条件定义本身，不是核验机制。**

### 6.5 为什么这一节值得单独存在，而不是并进「执行边界三问」

§3 执行边界三问解决的是"这一步该不该打断任务问人"；本节解决的是完全不同的一个问题——"这一整轮该不该算完"。两者容易被混为一谈，但失效模式不同：前者是执行者在单个动作上犹豫，后者是执行者在**整体进度评估**上系统性乐观。同一层机制盖不住两种问题，这也是为什么它没有被塞进 §3，而是单独成节。

## 7. 本地预算工具

[`tools/apply_budget.py`](../../tools/apply_budget.py) 使用Python标准库和本地SQLite事务，Agent负责调用；无需用户手写台账或配置。适用于同一私人工作区、本机文件系统上配合该协议的执行者。它不控制绕开协议直接调用的浏览器，也不替代Host的任务锁、权限或平台限额；共享网络盘、跨机器同时执行及Windows未实测的环境不作保证。没有该能力时继续可做的发现与准备，明确缺少硬性计数保障。

Agent已取得私人工作区路径后，将其填入 `JOB_WORKSPACE`，例如：

```bash
python3 tools/apply_budget.py --workspace "$JOB_WORKSPACE" init --target 150
python3 tools/apply_budget.py --workspace "$JOB_WORKSPACE" begin
python3 tools/apply_budget.py --workspace "$JOB_WORKSPACE" status
```

`init` 建立缺失的 `policies/pacing.json`、运行库及策略变更记录，保留已有文件；若发现根目录旧 `pacing.json` 而没有新配置，先拒绝默认初始化，由Agent按实际旧设置转换，避免静默提高旧上限。显式参数才调整已有目标或预算，目标不能高于预算。初始化不构成发送授权。`begin` 返回本轮 `run_id` 与配置哈希。每次发送按顺序：

1. `reserve --run <run_id> --key <稳定申请键> --details <JSON>`，详情记录公司、岗位、级别、渠道、材料版本；返回本次 `attempt_id`。拒绝占额时不发送。
2. 在外部动作前执行 `dispatch --run <run_id> --key <键> --attempt <attempt_id>`；它再次检查风险、日预算、配置与所有者，成功后才调用已有执行器。
3. 填写、上传、普通确认、最终提交和回读按既有授权完成。执行器/网页不能扩大授权；不要用预算工具批准一项用户没要求的动作。
4. `record --run <run_id> --key <键> --attempt <attempt_id> --outcome confirmed|pending|not_sent --evidence <实际结果证据>`。提交超时默认记待核实，不重发；已占额而尚未dispatch的项不能凭结果命令冒充成功。
5. `heartbeat --run <run_id>` 续租；每批读取状态，在当前轮目标或会话上限到达后 `finish --run <run_id> --reason round_target|session_limit`，有可执行日任务则新开一轮。不得因为完成一批就结束整个日任务。
6. `export` 只刷新 `ledger.md` 的 `apply-budget` 自动区块，保留原记录、跟进原话和其它正文。生成当日review时读取 `status`，记录配置哈希及实际成功/待核实/占额数量。

Python调用可用 `Budget.execute(run_id, application_key, submit_callback, details)` 走相同占额/dispatch/结果协议。回调调用已有执行器并返回 `status` 与可核实的 `evidence`；普通异常变待核实，不自动重试；进程崩溃保留发送中占额。

恢复时先只读检查旧执行器任务是否已结束；仍在执行不能抢占。租约到期且旧任务已确认停止后 `begin --recover`：未dispatch的占额释放，已dispatch未登记的项转待核实，旧 `run_id` 被撤销，旧所有者不能再次发送。`resolve --key <键> --outcome confirmed|not_sent --evidence <核实证据>` 只处理待核实项。新会话或跨日不能清除它们。过期发送者取得的回执应由当前会话只读核实后resolve，不让旧执行者恢复权限。

旧台账迁移：先读原台账与平台已联系状态，将有稳定键和证据的成功/不明项通过 `import --key <键> --outcome confirmed|pending --at <实际发送时间及偏移> --evidence <证据>` 导入，保留原记录；不知道是否发送过的岗位先待核实，不按“没有新键”认定未投。历史无法归日或匹配的项目列入review缺口，在查清相关范围前不宣称日计数完整。旧 `in_progress` 锁另需检查其执行器已停止，再 `clear-legacy-run --evidence <核实记录>`。旧占位参数先按已有用户设置转换为新字段，不默默提高旧日上限。

测试入口：`python3 -m unittest discover -s fixtures/02-apply -p 'test_*.py' -v`。测试使用虚构申请与隔离执行器，仅验证相应本地协议，不证明真实平台吞吐。配套[模块入口](README.md)、[执行Skill](SKILL.md)、[台账契约](../../docs/module-contracts.md#8-ledgermd--台账-)。
