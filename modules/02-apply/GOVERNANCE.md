# GOVERNANCE · 让自动化不失控的判断层

> 与 [`SKILL.md`](SKILL.md) 配套使用。本文件只讲判断，不讲执行步骤——"什么时候该停、什么时候可以继续、失败了算谁的"。所有参数默认值在 [`config/pacing.json`](config/pacing.json)，本文件不重复写死具体数字。

---

## 1. 节奏引擎：四层量级上限必须一起给

**只给一个"日总量"数字是危险的**——照抄一个脱离上下文的日总量，比不知道这个参数存在更危险。真正决定风险的是"单次会话跑多久、批次之间休息多久"，不是"一天投了多少"。

四层上限缺一不可，见 [`config/pacing.json`](config/pacing.json) 的字段说明：

1. **单日总量上限**——分摊在多次触发窗口上，不是一次性跑完
2. **单轮目标**——争取 2-3 轮达成日目标，不靠很多小批量拼凑
3. **单次会话批次上限**——一次连续运行的硬上限
4. **批次内量与批次间休息**——批次跑完接着跑下一批，不是休息完就收尾

**触发抖动**（随机延迟而非固定整点）、**页面停留随机化**、**浏览顺序不完全规律**、**不并行开多标签页**——这几条是行为模式层面的纪律，不是数字参数，写在 `pacing.json` 的注释里，具体取值由你自己校准。

⚠️ **本文件与 `pacing.json` 一律不给出"安全"的具体建议数字。** 所有默认值都标了来源等级（`默认建议值` / `纯占位待校准`），意思是**这些数字来自某一个人在自己账号上跑出来的经验，不是被验证过的通用安全值**。直接照抄的风险在于：你的账号历史、平台对你的信任积累、你所在的城市/行业竞争密度，都会影响什么样的节奏"安全"，这些变量本模块无法替你估计。

## 2. 熔断

**触发源限定为强语义信号**：验证码、异地登录提醒、异常操作提示、账号异常状态页。**不是**"命中率下降""跑得有点慢"这类正常波动。

**一旦触发，`apply-lock.json` 的 `risk_paused` 置 `true`**，此后所有自动触发**直接结束、不重试、不做任何投递相关操作**，优先级高于"今天数量没达标"这类任何目标。

**解除必须是显式的人工动作**，不能依赖"在对话里说一句"这类隐式确认——开源发布的版本必须给出一个确定的、有记录的解除入口，不能让"解除"这件事发生得悄无声息。⚠️ **本仓库目前唯一实现的解除入口是"改 `apply-lock.json` 的 `risk_paused` 字段"**——如果你的运行环境有更适合的方式（比如一条自定义命令），可以自己加，但那不是本仓库发布的一部分；不要假设有一条现成的、本仓库没写但"应该存在"的解除命令。

⛔ **不允许因为"已经过了一段时间、应该没事了"而自动恢复。** 熔断状态没有超时自愈机制，这是有意的设计——风控信号的持续时间对 agent 不可见，自动超时恢复等于在赌一个自己看不到的变量。

## 3. 执行边界三问

自动化流程里的失败分两种性质完全不同的情况，处理方式必须不同：

**遇到卡点时，按顺序自查：**

1. **这是风控/同意类信号吗？** → 是，停。不重试、不换方式绕过、不用"再试最后一次"这种理由继续。这条优先级最高
2. **这是纯技术执行问题吗？**（连接失败、超时、渲染卡顿、元素没点中）→ 是，按明确的重试规则自主处理：默认重试 1 次，连续失败 3 次以上再换方式重试，仍不行才升级到 L3 回报，附带失败步骤。**不为这类问题打断任务去问人**——问不是不能问，是不该问
3. **这是规则能裁决的业务判断吗？**（这条要不要投、要不要发这条打招呼语）→ 是，按既定规则自主判断，拿不准就按更保守的一侧判断，事后记录理由，不停下来问

**只有真正卡在"规则没覆盖、又不是技术问题、又不是风控信号"的情况，才值得打断汇报。**

## 4. 提前结束白名单

**只有以下四种情况可以提前收尾**，命中哪一种要写进 review 卡：

1. **命中风控信号**（熔断触发）
2. **候选池确实枯竭**——所有渠道各扫过一轮，且去重命中率持续很高（意味着大部分候选都已处理过）。⚠️ **如果本轮任务定义了结构化覆盖清单（见 §6），这一条必须由独立核验确认，不能自己判断"差不多枯竭了"**
3. **达成轮目标或日目标**
4. **触及单次会话上限**

**反面清单——以下都不构成提前结束的理由**：

- "逐条核对文本"（这是正常步骤的成本，不是可以跳过换速度的地方）
- "工具调用次数多"
- "感觉工作量大"
- "命中率看起来在下降"（下降不等于枯竭，见白名单第 2 条的区分）
- "跑得有点久了"

⛔ **这份反面清单本身也是一份需要独立核验的清单**——见 §6：执行者如果在收尾陈述里说出反面清单上的理由，独立核验子 agent 必须直接判定"不满足停止条件"，不接受这类理由作为收尾依据。

## 5. 汇报边界

**有明确数量/进度目标的任务，在目标达成之前，不主动停下来做阶段性总结，也不用"要不要继续"这类暗示性收尾结束任务。** 过程中出现的新情况（比如收到对方回复）记入台账备注即可，不需要单独打断任务去汇报。真正要收尾时，一次性给完整汇报（即每日 review 卡）。

这条和 §3 执行边界三问是两回事：一个管"要不要打断任务问问题"，一个管"要不要打断任务汇报进度"，默认答案都是不要，除非明确命中风控信号这类必须停的情况。

## 6. 长周期批量任务的收尾：结构化覆盖清单 + 独立核验

**这一节解决的是一个具体的、真实反复发生的失效模式**：即使把停止条件写得足够具体，执行 agent 仍然会在长会话里因为工作量大、命中率下降、会话变长这类疲劳类模式，自行判断"可以收尾了"——哪怕它自己刚刚在收尾陈述里承认"还有几个组合没扫完"，结论仍然是"可以停"。

**根因不是规则不够细。** 停止判断依赖执行者对自身进度的**叙述性自评**，而不是对**结构化状态的机械核对**。自然语言总结天然允许"基本""大部分""差不多"这类模糊量词，判断"是否该停"和"执行任务本身"由同一个身份、在同一次输出里完成，缺乏独立视角校验——这是一种结构性的利益冲突，靠给这个身份加更多文字规则解决不了，因为规则也是由同一个可能存在乐观偏差的判断过程去执行的。

**同一类问题补丁式修订三次以上仍复发，应该怀疑机制本身，不是继续加细则。**

### 6.1 什么任务需要这套机制

任何"有明确数量/覆盖目标、多轮次执行、执行者可能因为工作量大或战果变少而提前收尾"的自动化任务，**不限于本模块**。典型场景：扫描多个渠道 × 多个关键词组合、批量核实一份候选清单、任何"要枚举完一个有限但较大的集合"的批处理。

**不需要这套机制的场景**：单次触发只处理台账里已经确定的一批 JD（数量有限、范围本身就是台账内容，不存在"扫描空间还有多少没覆盖"这个问题）。是否需要，看任务本身是否存在一个"结构上可枚举、但执行者容易低估剩余规模"的搜索/扫描空间。

### 6.2 第一步：把任务范围拆解成结构化、可枚举的覆盖单元清单

**落地成独立文件，不是写在执行者的自然语言汇报里。** 覆盖单元要足够细、足够客观，能用"未开始 / 进行中 / 已完成"这种机械状态描述，不依赖主观判断。

最小字段设计（`runs/<date>-覆盖清单.json`，运行时状态文件，不是跨模块契约）：

```json
{
  "周期标识": "本轮的唯一标记，例如日期或批次号",
  "覆盖单元": {
    "<渠道>×<关键词组合1>": {
      "status": "not_started | in_progress | done",
      "最近处理时间": "ISO 时间戳",
      "本轮新增候选数": 0,
      "去重命中数": 0
    },
    "<渠道>×<关键词组合2>": { "...": "..." }
  }
}
```

**执行过程中要实时更新这份清单**——处理完一个单元立刻写状态，不要等任务结束时凭印象回忆补一份。这一步本身是关键：如果状态只在结束时批量回填，仍然会退化成"事后叙述"，失去机械核对的意义。

### 6.3 第二步：收尾判断权从执行者转移给一次独立的 agent 调用

主执行 agent 想要结束当前轮次之前，**必须调用一个独立的子 agent（全新上下文，看不到主执行 agent 的对话历史和自我叙述）**，给它一个范围明确、输入受限的任务：

- **只允许读取结构化状态文件**（覆盖清单 + `ledger.md` 今日记录 + `apply-lock.json`），**不接受主执行 agent 转述的"进度总结"作为输入**——这一条是这个机制生效的关键。如果子 agent 的判断依据里混入了主执行 agent 自己的叙述，独立性就被污染了
- 逐条对照 [§4 提前结束白名单](#4-提前结束白名单)，给出「满足 / 不满足」的布尔判断，**并写明依据的具体数字或状态**（不允许用"基本""大致"这类模糊措辞代替逐项核对）
- 如果任何一条不满足，明确返回"应继续执行"，并列出清单里所有仍处于 `not_started` 的覆盖单元
- ⛔ **如果主执行 agent 在准备移交给子 agent 的材料里出现 §4 反面清单上的措辞（"感觉工作量大""命中率在下降"等），子 agent 必须直接判定不满足停止条件，不需要再核对其他项**——这是反面清单的机械执行点

**独立核验的调用方式**：可以是同一 agent 产品里发起的一次独立子任务调用（例如 Claude Code 的 Task/Agent 工具），关键约束是**这次调用不带入主任务的对话历史**，只接收上面列出的结构化文件作为输入。如果你的 agent 运行时不支持发起独立子调用，退化方式是：**开一个全新的对话会话**，只把覆盖清单文件和台账贴进去，让它独立判断，再把结论带回主任务——效果等价，只是操作上多一步。

**主执行 agent 必须把这个独立判断当成收尾与否的唯一依据**：子 agent 说"应继续"，主执行 agent 就不能因为"自己觉得已经做了很多、读了很久、命中率变低"而自行推翻；子 agent 的判断和完整依据要写回覆盖清单文件（补一个 `独立核验结论` 字段），留下"这一步确实被独立核验过"的痕迹。

### 6.4 这个机制的价值边界

它解决的是"执行者用模糊叙述给自己找收尾借口"这一种失效模式，**不能替代"停止条件本身该怎么定义"这个更上游的判断**——条件定义得不合理，独立核验只会更精确地执行一个错误标准。所以这个机制必须和 §4 明确、可枚举、无歧义的停止条件搭配使用，不能单独依赖它。

**如果发现子 agent 反复卡在某条停止条件上给不出干脆的布尔判断，说明该回头修的是条件定义本身，不是核验机制。**

### 6.5 为什么这一节值得单独存在，而不是并进「执行边界三问」

§3 执行边界三问解决的是"这一步该不该打断任务问人"；本节解决的是完全不同的一个问题——"这一整轮该不该算完"。两者容易被混为一谈，但失效模式不同：前者是执行者在单个动作上犹豫，后者是执行者在**整体进度评估**上系统性乐观。同一层机制盖不住两种问题，这也是为什么它没有被塞进 §3，而是单独成节。
