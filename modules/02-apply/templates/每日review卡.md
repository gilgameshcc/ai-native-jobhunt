# 每日 review 卡模板

> 对应 `docs/module-contracts.md` §4 `runs/<date>-review.md`。这是"每天只 review 一次就够"能成立的唯一原因——它把本轮全部判断压成可审计的一页，不是让人翻日志。
> ⛔ 每个字段都写了"为什么要它 / 空着代表什么"，不要因为某天用不上就删掉这个字段——删掉之后，没有任何东西会提醒你去看它。

---

## 昨日执行

- **统计日期与时区**：〔按发送日；迟到确认回补原日〕
- **生效配置**：〔`policies/pacing.json` 的哈希、来源等级、日目标/日预算、轮目标与会话边界〕
- **触发次数**：〔本轮定时触发被调用了几次〕
- **实际发出数**：〔从运行证据统计的已确认唯一申请数，跟进不增加；原始历史未可靠迁移时注明缺口〕
- **待核实 / 发送中 / 已占额未发送 / 剩余预算**：〔分别列数，不能把后三项冒充成功〕
- **各轮结果与继续条件**：〔保留之前各轮，不用最后一轮覆盖；普通轮/会话边界到达后可续轮，实际调度入口/下次触发或阻塞单列〕
- **跳过数及原因分布**：〔按原因分类计数，例如：硬性排除条件命中 N 条 / 去重命中 N 条 / 待定级 N 条 / 打招呼语定制失败 N 条〕
- **风险信号**：〔本轮有没有出现过验证码/异地登录提醒/异常操作提示，哪怕最后没有触发熔断〕
- **熔断状态**：〔`risk_paused` 当前取值；如果是 true，附 `risk_note`〕

## 逐条台账

| 公司 | 岗位 | 定级 | 匹配度依据 | 简历版本 | 打招呼要点 | 状态 |
|---|---|---|---|---|---|---|
| | | | | | | 已投 / 待确认 / 失败 |

> 默认给出新增记录的索引和少量异常，不要求用户逐条审阅；唯一申请键、材料和结果证据在原记录中保留。后续沟通标跟进，不重复计数。

## 要你决策

- 〔阈值边缘的岗位：匹配度卡在临界值，投还是不投〕
- 〔HR 回复：索要简历 / 追问细节 / 面试邀约——这类需要你本人回应的〕
- 〔L2 自救阶梯里"定位不可靠、跳过了继续下一条"的记录——这些条目需要你决定是手工补上还是放弃〕

## 沉淀

- **新入库 JD 数**：〔本轮新采集/新看到的 JD 数量，喂给 `06-positioning` 的支线 A 输入〕
- **趋势信号**：〔如果本轮观察到值得记录的市场信号，简单提一句，详细分析交给 `06-positioning`〕

## 异常与降级路径

- 〔哪个 adapter 断言失败、失败在哪一级（L1/L2/L3）、当时怎么处理的〕

## 低产归因

> ⛔ **这是硬性字段，不是可选项。** 实际发出数明显低于轮目标/日目标，且不是因为熔断/候选池枯竭/会话上限时，必须写明真实原因，不许含糊带过。"投得少一些"不构成归因，"今天大部分岗位卡在待确认，因为定级模块本轮没跑"是一个合格的归因。

〔本轮如果产出正常，这一栏写"不适用——本轮产出符合预期"；如果不正常，必须写清楚原因〕

## ⭐ 独立核验记录（仅当本轮涉及结构化覆盖清单任务时填写）

- **本轮是否走完整核验**：是 / 否
- **核验结论**：满足停止条件 / 不满足，应继续
- **依据**：〔独立核验子 agent 给出的具体数字或状态，不接受模糊措辞〕
