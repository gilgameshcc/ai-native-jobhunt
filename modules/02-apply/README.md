# 02-apply · 判断闸门式自动投递与浏览器治理

> **v0.1.0** · 治理层方法论，**不是投递引擎**。零可执行代码——本模块和仓库其他部分一样是纯 markdown + 参数模板，不含任何真实平台的自动化实现。

---

## ⛔ 先读这一节，再读别的

**本模块交付的是"什么时候该停、什么时候可以继续、失败了算谁的"这套判断层**，不是一套能直接跑起来的浏览器自动化代码。

- **不教绕过任何技术防护措施**——验证码/滑块自动过、指纹伪装、代理与 IP 轮换、设备伪造。这是唯一一条会让风险从"你的账号"跳级到"仓库维护者的责任"的线，没有讨论余地
- **不采集他人个人信息**（HR、其他候选人的姓名/联系方式/简历）
- **不做全站爬取**——采集范围必须被你实际会投递的量约束，不提供"抓一遍整站职位库"这类功能
- **不提供无上限的投递配置**——本模块给的默认值全部带护栏，且**四层量级上限必须一起给**（缺一层配置视为不合规，见下）
- **不做简历隐藏提示词注入**（白字/图层藏指令操纵 HR 侧 AI 筛选系统）
- **措辞上不用"全自动 / 批量 / 海投"来描述投递本身或本模块的定位**——本模块的立场是"判断闸门式投递"：自动化的是**执行动作**，不是**判断本身**；判断闸门缺失时必须拒绝运行，见下方 fail closed。⚠️ **这条禁的是"投递方式/产品定位"的措辞，不禁"批量任务"作为通用技术术语的用法**——`GOVERNANCE.md` §6 讲的"长周期批量任务"指的是"有明确覆盖范围、需要多轮扫描才能完成"这一类任务的工程分类（不限于投递场景），不是在给"投递"本身贴"批量"标签，两者语境不同，不冲突

**底层执行引擎不要自己造。** 需要真实操作某个招聘平台网页时，直接用现成的、专门做这件事的开源实现（如 boss-agent-cli 这类 MCP 原生的浏览器操作工具，见 [`../../docs/ecosystem.md`](../../docs/ecosystem.md)）。本模块要做的是把**判断层**（该不该投、投多少、什么时候该停、出问题算谁的）套在那套执行引擎外面，而不是重新发明一遍浏览器自动化。

**⭐ 核心主张：判断闸门本身就是最好的反检测。** 海投工具被平台针对，不是因为"用了自动化"，是因为放弃了判断——转化率 100%、模板不变、节奏恒定，行为特征全线暴露。加了判断闸门之后，漏斗形态会天然接近真人（有真实的 skip、有真实的定制、有真实的犹豫），这不是伪装出来的效果，是判断本身产生的副作用。所以这个模块的正确读法不是"又一个投递自动化工具"，是"判断派方法论怎么落地成能长期运行的自动化"——参照坐标是 [`03-company-analysis`](../03-company-analysis/) 和 [`05-offer`](../05-offer/) 的判断纪律,不是效率派同类。

## I1 三问

### ① 单独用行不行？

**不建议单独用，且本模块的第一道规则就是拒绝在没有判断输入的情况下运行**（fail closed，见下）。它假设你已经有一套硬门槛和排除条件——不是因为技术上做不到脱离上游单独跑，而是脱离判断跑投递闭环，正是本模块存在的理由要反对的事。

如果你手上确实只有"我想自动化投递"这一个需求、还没有判断规则，本模块会先让你回答几个最小问题（见「开跑前」），而不是拿一套通用默认值直接开始跑。

### ② 依赖哪些模块的输出？

- **[`03-company-analysis/jd-triage`](../03-company-analysis/jd-triage/)**——硬门槛与排除条件、匹配度定级。没有它，本模块**拒绝运行**（fail closed），不会退化成"不判断也能投"
- **[`01-resume`](../01-resume/)**——简历版本与打招呼语素材，与 `02-apply` 同批首发。缺失时可用通用模板起步，但会明确警告文本同质化的风险
- **[`00-workspace`](../00-workspace/)**——台账契约（`ledger.md`）与工作区骨架

### ③ 缺了上游会退化成什么？

| 缺的 | 退化成什么 |
|---|---|
| **硬门槛 / 排除条件（`positioning.md`）** | **不运行。** 明确告诉你"缺少判断闸门，本模块拒绝在无判断状态下投递"，不提供任何绕过方式 |
| **定级结果（`triage/`）** | 同上——没有定级就没有可以自动执行的判断依据，**不会**退化成"你手工逐条确认要不要投"这种半自动模式，那本质上还是在用你的注意力去补一个不存在的判断层 |
| **简历版本与打招呼语（01-resume）** | 可用通用模板起步，但**明确警告**：模板化的打招呼语更容易被平台侧文本去重识别为批量投递，这不是本模块能兜底的风险 |
| **`branches.md`（探路分支）** | 找不到活跃分支时，一律按主线阈值判——不会给探路方向任何隐性放宽 |

## 目录里有什么

| 文件 | 是什么 |
|---|---|
| [`SKILL.md`](SKILL.md) | 交给 agent 的判断闸门式投递闭环剧本：定时触发 → 锁检查 → 渠道执行 → 门槛过滤 → 去重 → 定制 → 发送 → 登记 → 解锁 → 生成 review 卡 |
| [`GOVERNANCE.md`](GOVERNANCE.md) | 治理层：节奏引擎 / 熔断 / 执行边界三问 / 提前结束白名单 / 汇报边界 / ⭐ **结构化覆盖清单 + 独立核验**（长周期批量任务的收尾判断机制） |
| [`config/pacing.json`](config/pacing.json) | 节奏参数模板——四层量级上限、触发抖动、停留时长，**全部标来源等级，不是可以直接照抄的安全数字** |
| [`config/lock.schema.json`](config/lock.schema.json) | `apply-lock` 状态机字段定义 |
| [`templates/`](templates/) | 每日 review 卡 / 台账渠道字段补充 / 打招呼语骨架（不含真实文案） |

关联但不在本模块内：

- [`../../adapters/`](../../adapters/)——平台相关的东西（URL 拼法、按钮判定、字段定位）一律下沉到这里，声明式 JSON recipe，不是可执行代码，本模块只读取它，不定义它的具体内容
- [`../../docs/module-contracts.md`](../../docs/module-contracts.md)——`jobs/<batch>.md` 与 `runs/<date>-review.md` 两份跨模块契约在那里定义最小字段；`apply-lock.json` / `pacing.json` 是运行时状态与配置，不是跨模块契约，不出现在那份文档里

## 不做什么

- **不提供任何真实平台的适配代码**——`adapters/` 下只有一份完全虚构的格式示例，不对应任何真实网站
- **不给出一套可以直接照抄跑的具体阈值**——`pacing.json` 里每个数字都标了来源等级，且大多数是 `纯占位待校准` 或 `默认建议值`，抄来直接用意味着你在用一个人在自己账号上校准出来的节奏，跑在你自己的账号上
- **不做全站爬取**，采集范围由你实际会处理的投递量约束
- **不提供"确认过一次就一直信任"的机制**——发送前文本比对、每日 review、熔断解除都要求显式的、当次的确认
- **不替你点最终确认动作**（如果你的实现里有需要人工点击的环节，本模块的立场是那个点不该被自动化跳过）
