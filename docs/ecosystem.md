# 生态位：这个仓库和已有的开源求职项目有什么不一样

> 一句话：**已有项目做的是"把求职流程跑起来"，这个仓库做的是"跑之前和跑之后的判断"。**
>
> ⚠️ **star 数会变。** 下面每个数字都标了核实日期，请以 GitHub 当前显示为准；这里给数字只是为了说明"这条赛道不是空白"，不是为了排名。

## 一、这条赛道已经有三个数万 star 的全链路项目

| 项目 | 规模（核实日期） | 它解决什么 |
|---|---|---|
| [santifer/career-ops](https://github.com/santifer/career-ops) | 约 6.4 万 star（2026-08-16 经 GitHub API 核实） | 文件驱动 + agent 编排的求职全链路，覆盖岗位跟踪、简历定制、故事库 |
| [MadsLorentzen/ai-job-search](https://github.com/MadsLorentzen/ai-job-search) | 约 3.19 万 star（2026-08-16 经 GitHub API 核实） | 同类全链路，为 agent 命令行环境设计，含 `/interview`、`/outcome` 等阶段命令 |
| [srbhr/Resume-Matcher](https://github.com/srbhr/Resume-Matcher) | 约 2.81 万 star（2026-08-16 经 GitHub API 核实） | 简历与 JD 的匹配打分、关键词覆盖、定制建议 |

**所以：不要重新发明全案骨架。** 如果你要的是"把求职流程用文件和 agent 组织起来"，直接去读上面这几个项目，比从头设计省时间。这个仓库**不与它们竞争这一层**。

## 二、这个仓库补的是三块判断层空白

调研（2026-08-16，逐项目读文档与源码）确认下面三块在生态里基本是空的：

### 1. 面试前的策略性评估

相邻但**不重叠**的有三类项目：「反问清单」（给你一堆可以问的问题）、「故事库」（帮你组织自己的经历）、「模拟面试」（练答题）。

它们都不做这件事：**用投资人评估一门生意的框架，在面试前把这家公司过一遍，产出的问题是评估的副产品而不是起点。**

- career-ops 的故事库、ai-job-search 的 `/interview` 都停在"准备怎么答"这一侧
- VC 框架迁移到求职场景，目前止步于博客文章层面，没有落成可执行的方法论
- **AI 时代特有的风险透镜**（模型上移与薄封装 / 效果付费在没有中立裁决者时能否成立 / 成本通缩对按量计费的挤压 / 数据飞轮是真积累还是修辞）活跃在创投圈，**未见任何项目把它迁移到候选人视角**

→ [`../modules/03-company-analysis/interview-strategic-assessment/`](../modules/03-company-analysis/interview-strategic-assessment/)

### 2. offer 的横向决策

⚠️ **命名陷阱先说清楚**：在不少语境里 "job offer" 指的是**招聘启事**，不是**录用通知**。career-ops 里叫 `ofertas.md` 的文件比的是**岗位**，它自己的 README 明确写了"这不是在比较多个 offer"；它到手阶段的文件是条款朗读器，且**硬性禁止**输出结论、评分或红绿灯。

所以生态现状是：**计算层冗余**（真实时薪计算器满地都是，多数是 SEO 广告页）、**决策层空白**（没有人回答"排哪个前面、为什么、哪个假设变了会翻转"）。

→ [`../modules/05-offer/`](../modules/05-offer/)

### 3. 面试后的反馈闭环与方向优化

把每场面试变成一条**反馈边**（回去修正定位假设），而不是孤立事件。调研确认这是全生态最薄弱的一环——开源方案里只有 ai-job-search 的 `/outcome` 命令部分做到。

→ [`../modules/04-interview/`](../modules/04-interview/) · [`../modules/06-positioning/`](../modules/06-positioning/)

> 这两块（复盘协议 + 方向双环）**都在 v0.1 里**，见根 [`../CHANGELOG.md`](../CHANGELOG.md) 的八模块表。

## 三、执行层：不重复造，但现在有了包住它的判断层

**执行引擎本身**（真实平台的选择器/URL拼法/按钮判定）已经被多个活跃项目覆盖（boss-agent-cli、boss-helper 等）。**这个仓库不重造这一层，也不把它包装成自己的卖点**——[`adapters/`](../adapters/) 只发声明式 recipe 的**格式**说明与一份完全虚构平台的示例，不含任何真实招聘平台的实现细节。需要真实执行引擎时，直接用现成的开源实现。

⭐ **但 v0.1 新增了一层这些项目普遍没做的东西：包住执行引擎的判断层**（[`../modules/02-apply/`](../modules/02-apply/)）。这不是"又造一个投递工具"，是回答一个不同的问题——**"要不要执行、什么时候执行、执行到什么程度该停"**：

- career-ops / ai-job-search 的投递环节止步于"生成材料、人工提交"，没有做到在没有官方 API 的平台上让 agent 直接完成投递动作、同时应对平台行为层风控
- boss-agent-cli 架构更现代（MCP 原生、幂等去重、显式预算对象都值得学），但它的熔断是**单次调用级别**，不是跨会话持久化的系统状态；它自己也明确表态"不做反检测/规避工程"（`CDP must not be used as a risk-control bypass channel`）
- 这个仓库补的是：**缺判断闸门时 fail closed 拒绝运行**（不退化成无判断投递）+ **跨会话持久熔断**（一次风控信号后所有后续自动触发直接跳过，直到显式人工解除）+ **长周期批量任务的收尾判断走独立核验**（不由执行者自己叙述"做得差不多了"）

这层判断可以套在**任何**执行引擎上——不管你用 boss-agent-cli、boss-helper，还是自己写的浏览器脚本，`02-apply` 管的是"什么时候该让它跑、什么时候该让它停"，不管它具体怎么点页面。

> ⛔ 与此相关的边界见根 [`../README.md`](../README.md) 的「不做什么」一节——**不专门指导绕过技术防护（不管你自己用什么执行引擎）/ 不采集他人信息 / 不做全站爬取 / 不提供无上限配置**，这几条对判断层和执行层同样生效。

## 四、一句话对照

| | 已有全链路项目 | 这个仓库 |
|---|---|---|
| 目标 | 把流程跑起来、跑得更快 | **在每个决策点上给出可追溯的判断** |
| 简历 | 给 LLM 素材，按规则生成 | 事实池是唯一真相，**事实可追溯，表达可主动优化** |
| 岗位 | 匹配度打分 | 匹配度 + **硬性排除条件不可被匹配度换** |
| 面试 | 准备怎么答 | **先判断这家公司站不站得住**，问题是副产品 |
| offer | 条款整理 / 加权总分 | **排序 + 翻转点**，不出综合分 |
| ⭐ 投递 | 生成材料辅助人工提交，或无人值守无判断执行（后者已有账号被封的真实先例：AIHawk） | **判断闸门式投递**——缺闸门 fail closed；跨会话持久熔断；长周期收尾走独立核验 |
| 输出 | 一个分数 | 一个**能追到具体条件**的结论 + 它建立在哪些假设上 |

## 五、这份对照的局限

- 调研时间点是 **2026-08-16**，逐项目读了文档与源码，但**没有实际长期使用过**它们
- star 数与功能都会变；发现这里写的已经过时，**欢迎提 issue 指出**
- 这个仓库自己的方法论来自**一次真实求职实践（n=1）**，尚未在多人身上验证 —— 见 [`workspace-architecture.md`](workspace-architecture.md) 的局限声明
