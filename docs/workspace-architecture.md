# 工作区与 agent 架构

> **这份文档讲结构与判断，不讲怎么做。** 具体操作在各模块的 `SKILL.md` 里，本文不重复模块正文。
>
> 读它的目的是回答四个问题：这套东西凭什么这么设计 · 主链路长什么样 · agent 和你各干什么 · 为什么切成现在这几个模块。

---

## 这份文档是什么

一套**可复用的求职方法论骨架**：从"我在找什么"到"去哪一家"，中间每一步的产出都是文件，每一步的判断都写成了可以被复查的规则。

它从一次真实求职实践里抽象出来，但抽象掉了那次实践的全部具体内容——公司、人、数字都不在这里。留下的是结构。

**它不是**：一个求职工具、一个简历生成器、一套"投得更多"的方案。这里没有任何一条建议指向无差别大量投递，也没有任何一条指向绕过平台的技术防护措施。理由不只是合规——见 §五和 §八。

**受益人只有一个：找工作的那个人。** 本仓库不做任何"帮招聘方省力"的能力。

## 一、五条核心理念

工具会换，原则错了整套东西会垮。先定这五条，再谈目录和分工。

### 1. 工作区即数据库，文件即接口

不要靠对话记忆或某个 agent 的上下文窗口传递状态。**每一次状态变化都落地成文件**，下一个环节——不管是你、是下周的你、还是另一个 agent——只从文件读，不从"上一轮对话里说过什么"读。

这解决两个具体问题：

- **两个 agent 之间没有直接通道。** 浏览器侧和本地侧如果是两个不同的运行时，它们唯一的交接方式就是共享文件系统。
- **跨会话持久化。** 定时触发、并发状态、进度计数，全部必须是文件——会话级的状态在下一次会话里根本不存在（这条在 §五有一次付过学费的具体案例）。

落地形态见 [`00-workspace`](../modules/00-workspace/)，字段定义见 [文件契约](module-contracts.md)。

### 2. 单一事实来源：事实池是唯一真相

你的经历、指标、项目细节只在 `facts.md` 一个文件里维护。所有下游产物——各版本简历、首次接触话术、面试话术——**永远是它的子集**。

定制时**只能删不能改**：可以调顺序、可以删条目、可以把术语换成对方的原词。**不改数字、不改事实、不改组织名、不改时间。**

这条的价值不在整洁，在**防止 AI 在多轮迭代中悄悄编造和漂移**。没有它，十几个版本迭代下来，简历上的数字会不知不觉"越写越好看"——每一版都只比上一版夸张一点点，每一步你都觉得可以接受，直到面试时被问穿。

### 3. 主链路讲事实，定位与优势区讲观点，两者不互相复述

同一段经历会在两处被引用：「你是谁」（定位、优势提炼）和「你做过什么」（经历、项目描述）。**表述方式必须分工**——定位区总结规律和判断，经历区列举可验证的事实。

**如果两处写的是同一句话，说明要么定位是空话、要么经历没被真正提炼过。** 这是一条可以自查的判据，不是修辞建议。

### 4. 硬约束优先于灵活性

有几类规则必须写成**不可协商的硬约束**，而不是"建议"，因为违反它们的后果不可逆：

- **单一事实来源** —— 一旦被发现数字对不上，信任成本极高，且无法解释
- **平台风险信号出现即停** —— 主渠道断掉不可逆（见 §五）
- **输出格式硬约束**（比如简历必须单页）—— 这类通常有明确的物理或制度原因，不是审美偏好

判据是「违反的后果可不可逆」。可逆的写成建议，不可逆的写成硬约束。

### 5. 渐进式自动化：先做深度，再扩范围

**"覆盖更多岗位"和"每个岗位都判断到位"是两个独立的能力维度，不要用前者的名义牺牲后者。**

建设顺序：先把「匹配度怎么判、定制规则怎么定、首次接触怎么写」这套判断质量做扎实——这部分只能靠人和 agent 反复对齐规则来沉淀，工具帮不上忙。范围（覆盖多少城市、多少关键词、多少候选）是更容易靠增加执行时间线性扩大的部分。

**顺序反了就退化成无差别大量投递**——用高置信度的动作，重复执行低置信度的判断。这是整套方法论里最容易被工程习惯推翻的一条。

## 二、主链路：五个阶段

### 阶段 0｜职业定位

**做什么**：把「我想要什么、我能提供什么、什么算达标」写清楚，作为后面所有判断的标尺。

**产出**：目标形象 · 核心优势（不超过三四条，讲观点不讲事实）· **必要条件**（不满足就不投/不去）· **加分条件**（满足越多越好，但单条不构成否决）· 硬性排除条件 · 语言表达规范。

**谁做**：核心判断只能由你本人做——尤其涉及取舍的那部分（愿不愿意为了平台让渡别的、愿不愿意做转型岗）。**agent 不替你决定，只在信息不全时提示「这里需要你确认」。**

**为什么放第一**：没有稳定的参照系，后面每一步都会退化成"看到什么投什么"——判断匹配度、定制简历、写首次接触，全部需要一个不用每次重新论证的标尺。

> ⚠️ **必要条件与加分条件不可互换。** 加分项再多也换不掉一条必要条件。这条纪律在岗位定级、offer 排序等几个模块里都出现过，**犯的是同一类错**。

### 阶段 1｜事实池

**做什么**：把全部可用素材整理成结构化内容池——不是一份简历，是简历的**原材料仓库**。

**结构要点**：

- 按经历/项目分块，每块下面列**多个备选表述**（不同详略、不同侧重），供后续挑选，而不是每次定制都重新组织语言
- 每个指标标注口径和来源（哪一年、怎么算的），防止不同版本引用时漂移
- 明确记录**已裁定作废的旧表述**，防止未来某次定制不小心抄回旧版
- 末尾放语言规范：禁用词、术语统一、格式规则

**硬约束**：这里是唯一事实来源。**新增任何数字必须先经你确认才能写入**；反过来，其他任何文件里出现的事实性表述，理论上都应该能在这里找到出处。

### 阶段 2｜简历生成与定制

**做什么**：针对一份具体的岗位描述，从事实池摘录内容，生成定制稿，并保证格式合规。

**「只改这几处」原则**——定制的改动面要显式列白名单，而不是让生成过程自由发挥。典型白名单只有四项：

1. 优势条目的**顺序**（对方强调什么能力，对应优势往前排）
2. **术语替换**（用对方的原词替换同义表述）
3. 模块内条目的**排序**
4. 可选条目的**增删**（哪些经历块出不出现）

**明确不改**：数字、事实、组织名、时间。

**版本策略**：不要每个岗位都从零定制。维护少量几个基础版本，日常从最接近的那个改；只有高优先级岗位才值得深度定制。**版本数量本身也要设上限**——每多一个版本，日后维护事实一致性的成本就多一份。

**工程化**：定制稿到最终 PDF 应该是一步脚本，且脚本要能报告「是否单页、还剩多少余量」这类硬约束的验证结果，不靠人眼每次看排版有没有溢出。

### 阶段 3｜agent 驱动投递

最适合、也最需要自动化的一环，同时是**风险最高**的一环。拆成四步：采集 → 分析定级 → 首次接触 → 台账登记与去重。

- **采集**：只做客观抽取，不做判断——判断留给下一步。这一步的产出是 `jobs/<batch>.md`。
  > ⭐ 抽取时**顺手记下"这条是怎么进来的"**（搜索命中 / 平台推荐 / 对方主动推来 / 中间人转介）。定级用不到它，所以它看起来最像能省的那一栏——恰恰相反：它是阶段 6 判断"你的搜索词是不是在漂移"的**唯一输入**，而且**事后补不回来**。
- **分析与定级**：对照阶段 0 的标尺打分、分级，产出 `triage/<date>-定级结果.md`。**硬性排除条件要显式判定并直接排除**，不能用"匹配度很高所以放宽一下"去覆盖——这类条件本质上不可交易。见 [`jd-triage`](../modules/03-company-analysis/jd-triage/)。
  > ⚠️ **原文 vs 判断分在两个目录里**：`jobs/` 只放 JD 原文，`triage/` 放你对它的判断。把判断写回原文文件里，下次就分不清哪句是招聘方说的、哪句是你想的了。
- **首次接触**：多数平台的机制是「第一句话决定简历会不会被认真看」，所以这一步不是简历的附属品，而应该承载**最高密度的信息**：身份定位 + 最相关的硬指标 + 核心优势 + 针对这个岗位的具体观察 + 明确的下一步。做成模板体系，用真实岗位内容填充变量，**禁止发送时留占位符、禁止发空话**。
- **登记与去重**：每次接触都登记进 `ledger.md`；**发送前必须先查是否已经联系过**。

> ⛔ **这一阶段的边界不在「是否自动化」上，在「是否绕过平台的技术防护措施」和「是否碰他人数据」上。** 前者守死，后者守死；在这两条之内，判断闸门式的自动化是本方法论明确支持的做法。理由见 §五开头。

### 阶段 4｜面试：评估 / 执行 / 复盘

**面试不只是被评估，也是你对目标组织做一次结构化尽调的唯一窗口期。** 多数人把这个窗口浪费在转述和自述这层信息上，不核查、不追问、不用框架审视商业模式，最后的去留决定是拍脑袋。

分三层：

- **面试前**：多框架审视（真需求 / 可持续性 / 阶段判断 / AI 时代特有风险透镜）→ 材料交叉核查与可信度标注 → 按提问对象分层的问题清单 → 红旗绿旗成对判据 + Kill Switch 问题。**问题是评估的副产品，不是起点。** 见 [`interview-strategic-assessment`](../modules/03-company-analysis/interview-strategic-assessment/)。
- **面试中**：按一页纸清单现场记录，实时给答案分类；观察类问题用行为化追问验证，不停留在标签化回答。
- **面试后（当天）**：记录被问到的问题、答得不好的地方、对方关注点与你预设定位是否对得上；红旗绿旗的实测结果记成**证实 / 证伪 / 未验证三态**——"未验证"不等于"证伪"。

### ⭐ 阶段 4 不是终点，是一条指回阶段 0 的反馈边

如果同一类问题反复出现且回答效果不好，说明事实池里对应部分的表述需要修订，**或者定位本身需要调整**。

这不是"改简历"，是**把每一次面试当成对定位假设的一次真实市场检验**。少了这条反馈边，投得越多，用同一个错误假设重复犯错的次数也越多。

### 收口：offer 排序

拿到多个录用通知后，把「这门生意成不成」和「我要不要去」**显式拆成两个问题**——两者不是同一件事。见 [`05-offer`](../modules/05-offer/)。

## 三、三条支线

主链路是拿到 offer 的最短路径。但只跑主链路，容易陷入**用一个从未被检验过的定位假设，不断重复同一种动作**。

三条支线的作用不是让主链路更快，是**持续验证定位假设本身**。

| 支线 | 数据源 | 它在验证什么 |
|---|---|---|
| **A · 市场情报** | 定期重跑一批岗位描述的高频词与职责模式分析 | 「市场对这个角色的定义」有没有变；你的定位表述是否需要跟进 |
| **B · 目标公司清单** | 先框定一批高契合度的组织，再围绕它们主动创造机会 | 「等关键词命中」之外的机会来源存不存在；理想雇主画像是否准确 |
| **C · 行业动态** | 目标赛道的资金、政策、技术趋势 | 「现在是不是投这个方向的好时机」；也是面试中展现懂行业而不只是懂岗位的谈资来源 |

三条支线共同的设计约束：

- **支线 A 的输出反哺阶段 0 和阶段 1**，不直接进主链路。它改的是标尺，不是当天投哪几个。
- **支线 B 的正确形态是「agent 检索候选 + 人工审核门禁 + 不自动生效」。** 让 agent 自主发现并自动把新目标写进正式清单，是没有先例、也不该开的口子；检索候选、人工决定要不要转正，是已被验证过的模式。转正后的目标在下一轮检索里自动当作已知跳过，天然形成增量。
- **支线 C 更适合低频率、人工主导。** agent 的角色是信息聚合和摘要，不是自动判断。

> ⚠️ 支线的信号天然是**单次的、看起来像噪声的**。主链路靠"重复出现 + 样本门槛"防止被一两次拒绝带偏，**同一套门槛会把支线信号当噪声滤掉**。所以：登记免费、不设门槛；门槛只加在「登记 → 开一条探路分支」这一步，且分支必须自带证伪判据和截止日期。

## 四、agent 角色分工

| 谁 | 负责 | 不负责 |
|---|---|---|
| **浏览器侧 agent** | 打开页面、抽取结构化岗位信息、执行写动作、把结果落成文件 | **不做匹配度判断，不做投递决策** |
| **本地侧 agent** | 读已落地的文件：打分定级、生成定制稿、起草评估与复盘、汇总趋势 | **无法操作浏览器**，只处理文件；不新增事实 |
| **你本人** | 一切主观取舍、定位与事实池的最终拍板、面试、深度沟通 | 不需要做机械性的抽取、排版、格式核对 |

### ⭐ 两个 agent 之间没有直接通道

这是整套架构里最关键的一条工程事实：**浏览器侧和本地侧通常是两个不同的运行时，它们不能互相调用，唯一的交接方式是共享文件系统。**

所以「文件即接口」不是一个优雅的比喻，是**唯一可行的实现**。一旦有人试图让两侧直接对话，第一件坏掉的事就是可复查性——你再也说不清某个判断是基于什么材料做出的。

### 分工判据

**一件事能不能交给 agent 自主执行，看它是不是「给定规则就能确定性判断」的事。**

- 匹配度算不算达标、格式是不是单页 → 有明确判定标准，交给 agent
- 「要不要为了这个机会让渡某条必要条件」 → 不管规则写得多细，都留给人

## 五、治理：让自动化不失控的判断层

> **本节只讲判断，不讲实现。** 具体参数、状态字段、熔断实现在对应模块里，且都带默认值与护栏。**本文不给任何参数值**——照抄一个脱离上下文的数字，比不知道这个参数存在更危险。

### 5.0 为什么需要节奏与熔断这一层

先说一个反直觉的结论：**放弃判断的无差别大量投递，最先垮掉的不是伦理，是技术上跑不长。**

原因是**行为特征与真人形态完全不同**——不做判断，就必然在节奏、内容和取舍上留下一整套与人不一致的痕迹。这里不逐条展开是有意的：那份清单对读者没有增量，对想拿它当规避对照表的人反而有。

反过来，**判断闸门本身就产生了正确的行为形态**：硬门槛和去重产生真实的跳过，漏斗形态与人一致；内容按岗位真实信息定制，没有可被文本去重的模板；作息窗口和量级上限让节奏落在人类范围内。

**所以节奏与熔断不是为了"看起来像人"，是判断做扎实之后的自然结果。** 这也是本方法论和"跑得更快"类工具的分界：前者的节奏是判断的副产品，后者的节奏是刻意加上去的伪装——后者会一直需要对抗，前者不需要。

同样的道理，**熔断的优先级高于任何数量目标**：平台发出风险控制或需要本人确认的信号时，立即停止，不重试、不换路径。这条不可协商。

### 5.1 跨会话状态用文件锁，不用会话级任务列表

**这是付过学费的一条。**

原设计以为「检查任务是否处于进行中」能防止定时触发时的重复执行。实测：**定时触发的每一次都是全新会话，看到的任务列表永远是空的——这个检查从未真正生效过。**

它比"设计得不好"更糟：它是一个**看起来在工作、实际从未被观测到生效过的闸门**，而一个从没被观测到拦住过的闸门，和一个坏掉的闸门无法区分。

**结论**：任务级状态（跑没跑完、今天有没有达标、是否处于暂停）必须落地成文件，且解除暂停必须是**显式的人工动作**（改字段或跑一条命令），不能依赖"在对话里说一句"。

### 5.2 ⭐ 进度必须现读台账重新数

不信锁文件里的旧计数，**更不信会话记忆**。

这是全文通用性最强的一条 agent 工程原则，适用范围远远超出求职：**定时触发的任务，状态只能从文件重建。** 任何"我记得刚才做到第几条"都是幻觉——那个"刚才"在下一次触发时并不存在。

代价是每次触发多读一个文件。收益是这套东西能连续跑几个月而不发生静默的重复或漏做。

### 5.3 执行边界三问

自动化流程里的失败分成性质完全不同的三类，混为一谈会导致两种相反的问题：要么把纯技术故障当成大事反复打断人，要么把真正需要人决策的事自作主张处理掉。

卡住时按顺序自查：

1. **这是风险控制或需要本人同意的信号吗？** → 是则**停**。不重试、不换方式、不绕过。
2. **这是纯技术故障吗？**（连接失败、超时、渲染卡顿、元素没点中）→ 是则**自己重试一次**，按既定规则处理。
   ⭐ **这里的关键不是"能不能问"，是"不该问"。** 为一次超时打断人，训练出来的是一个不敢自己走完流程的 agent。
3. **这是已有规则能裁决的业务判断吗？** → 是则**自己裁决**，拿不准就按更保守的一侧走，事后记录理由。

只有真正卡在「规则没覆盖、又不是技术问题、又不是风险信号」的情况，才值得打断汇报。

### 5.4 汇报边界

**目标达成前不主动中途汇报。** 过程中出现的新情况记进台账备注即可，不单独打断任务。真正收尾时一次性给完整汇报。

**没有执行动作时只回一句话说明原因**——不需要为"今天因为处于暂停状态所以没跑"写一份报告。

这条和 5.3 是两回事：一个管「要不要打断任务问问题」，一个管「要不要打断任务汇报进度」。**默认答案都是不要。**

> ⚠️ 与之配套的是一份**反面清单**：「逐条核对文本」「工具调用次数多」「感觉工作量大」——**都不构成提前收尾的理由**，它们只是正常步骤的成本。不写这份清单，agent 会自己发明提前结束的借口。

## 六、参考实现选型

这一节给的是**具体建议**，不是原则。每条写清楚：解决什么问题、值不值得抄、抄的时候注意什么。

### ⭐ 先说最重要的一条：底层执行引擎不要自己造

**底层投递引擎建议直接用 `boss-agent-cli` 这类现成的开源实现。**

理由很直接：这套方法论的价值在**判断层**——定位标尺、定级规则、内容治理、跨会话治理、面试前评估、offer 排序。执行层（打开页面、点按钮、抽字段）是一件已经有更早、更专注的活跃项目在做的事，在那个维度继续加投入，边际价值在下降。

**把执行层包装成自己的卖点，是这套方法论最容易走错的一步。** 那场竞争赢面不大，也不是价值所在。正确的姿态是：**方法论骨架和平台实现分开发布**，实现层明确写成"这是一个可替换的示例，底层引擎可以直接换成现成的开源实现"。

### 1. 把操作原语封装成工具层，而不是写成一段自然语言指令

**解决什么**：可移植性。如果浏览器操作规则只以自然语言写在 agent 配置文件里，换一个运行时这套规则要被重新"理解"一遍，理解偏差不可控。封装成结构化工具（参数和返回值都是定义好的），调用方式就与用哪个 agent 客户端无关了。

**值不值得抄**：⭐ **最值得的一条架构决策。** 如果这套东西要给别人用，这是对"移植性"最直接的答案。

**注意什么**：**分层要切干净**——操作原语进工具层，判断规则（定级、定制、治理）留在配置文件层。两者揉在一起，等于既没拿到可移植性，又失去了规则的可读性。

### 2. 幂等去重

**解决什么**：重复接触。靠"从页面上当前显示的状态反推是否已经联系过"是一种界面层的启发式，页面一改版就失效，而且失效是静默的。

**值不值得抄**：值得，而且成本很低。

**注意什么**：**不需要做完整的工具化改造也能先抄这一条**——在本地维护一份「已接触过的目标」记录即可，不完全依赖每次重新读页面判断。⚠️ 记录键要选**平台无关的稳定组合**，不要用某个平台的内部 ID，否则这份记录换平台就废了。

### 3. 显式的预算对象

**解决什么**：把上限从"写在文档里、靠 agent 自觉遵守的一句话"，变成**动作开始前设好、用完就停、由代码强制**的结构化对象。

**值不值得抄**：值得，且这是本方法论目前最明确的一个升级项——纯文字规则要靠 agent 每次重新理解并自己数数，这件事不可靠。

**注意什么**：**多层上限必须一起给。** 只给一个日总量，会被照抄成"一口气跑完日总量"——那是完全不同的风险剖面。真正决定形态的是单次会话上限和批次间隔，不是日总量。另外，**预算耗尽和风险信号应该触发同一个熔断入口**，不要写成两套逻辑。

### 4. 平台能力矩阵

**解决什么**：多平台扩展时的状态声明——每个平台支持到什么程度（完整支持 / 只读 / 占位未支持）写得清清楚楚。

**值不值得抄**：**只有在确实要扩展到第二个平台时才抄。** 单平台阶段做这个是提前抽象。

**注意什么**：能力矩阵是**给使用者看的承诺**，不是内部备忘。写"占位未支持"比不写这个平台更有价值——它防止使用者花两小时才发现某条路走不通。

### 5. 状态机的最小单元测试

**解决什么**：治理层（并发状态、熔断、定级阈值）如果完全是自然语言规则，靠 agent 每次重新理解执行，**没有任何东西能验证这些状态转换逻辑本身写对了没有**。

**值不值得抄**：值得，且成本很低——只覆盖确定性最强的那部分就够（给定今日已完成数量和暂停状态，触发时应该怎么判断）。

**注意什么**：⭐ **每条规则要有一对「该触发 / 不该触发」样本。** 只测"该触发"的那一半，就无法区分"规则有效"和"规则永远返回真"。一个从没被观测到拦住过什么的闸门，和一个坏掉的闸门无法区分——这条和 §5.1 的教训是同一个命题。

## 七、为什么这样切模块

一个"求职全案"很容易长成一坨互相依赖的大泥球，改一处要动全身。五条约束，每条对应一个具体机制。

### I1 · 每个模块独立可用

**单独拿走任一模块都能跑，不要求先装全套。**

这不只是体贴。它的真实作用是**降低采纳门槛**：使用者可以只用 offer 排序，完全不接受这里的简历方法论。**任何一个模块要求"你得先接受我的世界观"，它的实际使用率就会趋近于零。**

实现方式是每个模块的 README 都要正面回答三问：单独用行不行 / 依赖哪些模块的输出 / 缺了上游会退化成什么。**第三问答不出来，说明耦合太紧，该拆。**

### I2 · 模块之间只通过文件契约耦合，不通过代码调用

**契约 = 一个 markdown 文件名 + 几个最小字段。** 完整定义见 [`module-contracts.md`](module-contracts.md)。

模块内部随便改，只要契约不变就不会打断下游。这也是 §四那条"两个 agent 靠文件交接"的模式向上泛化的结果。

三条契约纪律：

- **任一消费者在上游文件缺失时必须能降级运行**——退化成"需要你手工补这几项"，**不是报错退出**。这是 I1 的技术实现。
- **契约文件是 markdown，不是 schema。** 结构化字段只在必须索引时出现，且永远附文本上下文。
- **契约里不出现平台专有字段**（某个网站的按钮状态、职位 ID）。

### I3 · 平台相关的一律下沉到适配层

**主干保持平台无关。** 页面结构、字段位置、交互细节会变，方法论不会。

**判据非常硬：主干模块里出现任何平台专有名词都算设计错误。** 不是"尽量避免"，是设计错误——因为它意味着这个模块的寿命被绑定在了一个你控制不了的东西上。

适配层用**声明式配置而不是可执行代码**，理由有三：产出的是数据，可 diff、可回滚、可人工审；动作白名单能在运行时强制（声明一个定位符 ≠ 授权对它做动作）；公开的是一组语义模式而不是一份精确指纹，失效时可以重新探测自愈。

⛔ 适配层只放页面语义，**不放任何账号数据、本机路径、个人搜索参数**——后者留在使用者本机，不进版本库。

### I4 · 每个模块自带版本号、变更日志、和一节「不做什么」

- **版本号**让使用者知道能不能安全升级：不动契约 = patch，动契约 = minor 且必须写迁移说明，契约被删或改名 = major。
- ⭐ **「不做什么」是防止边界被撑爆的唯一机制。** 后来的贡献者不会读你的规划文档，只会读模块 README。**边界不写在模块里，它就不存在。**

### I5 · 三段式区块 + 三级自救阶梯

零可执行依赖只保证装得上，不保证**用得起来**。I5 是"可自助"的技术实现。

**三级自救阶梯**（什么时候才轮到人）：

| 级 | 行为 |
|---|---|
| **L1** | 有现成规则就直接走，**不问** |
| **L2** | 没有规则就用语义理解自己走通，**并把学到的写回去沉淀**（模板、配置、契约文件）——下次这件事回到 L1 |
| **L3** | 实在不行才回报人，且必须给：**症状 + 已经试过什么 + 建议你做什么** |

⛔ **不许一出问题就让人接管。** 这条阶梯是 §5.3「执行边界三问」从投递场景到全仓的泛化。

**三段式区块**（轮到人时给什么）——每个模块的 `SKILL.md` 必须自带这三段：

1. **「开跑前」** —— 要什么 / 缺了退化成什么 / **最小可接受形态**
2. **「来源标注」** —— `你给的` / `公开可查` / `我推测的`
3. **「不对劲的时候」** —— 症状 → 最可能原因 → 你下一句该说什么

⛔ 必须是 markdown 区块，**不能做成一个诊断工具**——排查的执行者是使用者的 agent，仓库只提供判据。

## 八、局限与未解决的问题

⭐ **诚实声明比伪装成熟更能建立信任。** 以下都是真实的空缺，不是谦辞。

### 这套方法论来自一次真实求职实践，n=1

它跑通过一次，跑了几个月，主链路和治理层都被真实使用过。**但它没有在多个人身上验证过。**

这意味着几件具体的事：

- **阈值和参数只是一个人的校准结果**，不是被统计验证的推荐值。仓库里所有阈值都参数化留空，并标注来源等级（`实践校准` / `默认建议值` / `纯占位待校准`）——**不要照抄，要按自己的情况重新标定**。
- **"这条规则有效"目前的证据强度是一次实践 + 一次事后归因**，不是对照实验。有些规则可能只是没被证伪过。
- **样本偏差不可忽略**：一个人的行业、职级、地域、目标类型，都会系统性地影响哪些环节是瓶颈。你的瓶颈很可能不在这里被强调的地方。

### 这几件事没有人测过（不是我们没查，是文献里没有）

README 与 CHANGELOG 里承诺的那份清单就是这一节。四条，逐条给出我们为此**不写什么**：

- **同一批人在 AI 重度使用 / 轻度使用的环境里，技能增长差异有多大** —— 学习侧至今没有对照研究。因此本仓任何"进这家 AI 更成熟的公司你会成长更快"的说法都不成立，我们也不写。
- **"某个具体岗位会不会被 AI 取代"** —— 公开证据全部停在职业层，落到"某公司某岗位"是外推。凡涉及此类判断，一律标 `我推测的`。
- **招聘页构成能否代理经营状况** —— 无任何验证，仅作观察角度，不作为结论性判据。
- **本仓每一条阈值** —— 见上面"样本 n=1"。没有一条经过多人校准。

### 其他已知空缺

- **文件驱动的工作区依赖严格的纪律。** 只要有一次偷懒直接改了下游文件而没经过上游事实来源，「单一事实来源」就会在实践中被悄悄破坏，且不容易察觉。需要定期人工审计一致性——目前没有自动检查。
- **agent 自主判断的边界依赖规则写得够不够细。** 规则有空白的地方，agent 大概率会做出让人不满意的默认选择（提前收尾、误判该不该停）。这些空白只能靠实际运行中暴露问题后反复补丁式修订，**没有办法一次性写全**。
- **平台机制本身会变。** 整套设计假设了当前招聘平台的产品机制（比如「第一句话决定简历会不会被认真看」）。机制一变，阶段 3 里对应环节的权重需要重新评估。
- **适配层会失效。** 页面语义随时可能变，且失效是静默的——不会有报错，只会开始返回空结果。这是把平台相关的东西下沉到适配层的原因，也是这一层需要社区维护的原因。
- **市场情报支线和面试后反馈闭环，目前是最薄弱的两环。** 结构定下来了，但真实运行的样本量最少，参考价值低于主链路的其他部分。
