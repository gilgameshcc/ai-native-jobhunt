# fixtures —— 自测语料

> **这些文件不是示例，是测试固件。** 想看"用起来长什么样"请去 [`../examples/`](../examples/)。

## 为什么需要它

一个模块的判断规则可能长这样：*"硬性排除条件不满足 → 判不投"*。
你怎么知道这条规则真的在起作用？

跑一遍看到"判了不投"**不够** —— 一条对**所有**输入都判"不投"的坏规则，和一条正确的规则，在这一次观察里**长得一模一样**。

> **一条从没被观测到"该放行时放行"的规则，和一条坏掉的规则无法区分。**

所以每条会做判断的规则，都要配**一对**样本：

| | 样本 | 期望 |
|---|---|---|
| 正向 | 该触发的输入 | 规则**必须**触发 |
| 反向 | 不该触发的输入 | 规则**必须**静默 |

**同时触发、或同时不触发 = 这条规则没有区分力 = 重写或删掉它。**

## 目录约定

```
fixtures/
├── README.md            本文件
├── <模块>/
│   ├── <规则名>.hit.md      该触发的输入
│   ├── <规则名>.miss.md     不该触发的输入
│   └── expected.md          这一对的期望结果与判据（一句话说清"凭什么说它对了"）
```

## 三条纪律

1. **全部虚构，从零编。** 不摘录任何真实素材——真实材料即使脱敏，仍然携带可反查的结构与巧合。虚构公司名统一用：纬度智能 / 恒平科技 / 青栈网络
2. **一对样本的差异要尽量小。** 两份样本只在"被测规则关心的那一点"上不同，其余尽量一致——差异越大，通过测试越说明不了问题
3. ⭐ **fixtures 验的是规则的区分力，验不了阈值的标定值。** "同类问题出现 3 次才改事实池"里的 3 是编的。所以所有阈值必须**参数化 + 标来源等级**（`实践校准` / `默认建议值` / `纯占位待校准`），不要指望 fixtures 能证明某个具体数字是对的

### ⚠️ 两条读这份表时要注意的

1. **"全部 PASS"是可疑结果。** 某一轮里某个模块全过，只说明**那一轮没有任何一条判据被固件推着改进** —— 上一轮同一个模块 5 对里有 2 对 FAIL，直接改出了两个版本。各 `expected.md` 里按字面记了这句话。
2. ⭐ **有一对虽然 PASS，但它的决策后果在那条路径上恒同** —— 试遍了构造不出反例，**如实报出而没有假装它有区分力**。真正有决策后果的那条路径见上面的未覆盖清单。
